# Post-Enrichment Audit Reference

Three structured audit phases for workshop content quality, designed to run
after initial content generation (workshop-do) and the verify-content quality
gate. These phases slot into workshop-act's existing fix-and-test loop.

---

## When to Use

These audit phases are RECOMMENDED (not REQUIRED). They are most valuable when:

- Workshop content was generated by an LLM or scaffolded from templates
- The workshop covers a product with extensive documentation
- The workshop is part of a multi-workshop catalog

Skip for simple workshops where the author manually wrote and tested every command.

---

## Phase A — Correctness Audit

**Goal:** Verify that every command, manifest, and console path in the workshop
matches the product documentation.

**Process:**

1. Extract product docs (if not already done):
   ```bash
   pdftotext <product-docs>.pdf /tmp/<slug>-docs/<name>.txt
   ```

2. For each module page, check:
   - Every `oc` command matches the doc syntax (correct flags, resource names, API versions)
   - Every YAML manifest uses the correct `apiVersion`, `kind`, and field names
   - Console navigation paths match the actual product UI
   - Expected output in `=== Verify` sections is realistic

3. Ground every fix in a doc extraction reference:
   ```
   Fix: changed `apiVersion: serving.kserve.io/v1alpha1` to `v1beta1`
   Evidence: /tmp/llmd-docs/model-serving.txt:142 — "apiVersion: serving.kserve.io/v1beta1"
   ```

**Self-check:**

- [ ] All commands match doc syntax
- [ ] CRD apiVersions are correct for the target product version
- [ ] Console navigation paths reference real UI elements
- [ ] `=== Verify` output is based on actual product behavior
- [ ] Balanced `----` fences on all code blocks
- [ ] `subs="attributes"` on blocks with `{...}` placeholders
- [ ] No `// TODO(enrichment)` markers introduced

---

## Phase B — Deduplication Audit

**Goal:** Identify and reduce duplicated walkthroughs across modules or across
workshops in a catalog, while maintaining standalone coherence.

**Process:**

1. Identify duplication by scanning for:
   - Identical or near-identical `oc` command sequences across modules
   - Repeated YAML manifests that appear in multiple workshops
   - Copy-pasted getting-connected or setup steps beyond the standard template

2. For each duplicate, decide:
   - **Same workshop, different modules:** Extract to a shared section or use
     forward/back xrefs within the workshop
   - **Different workshops in a catalog:** Replace with an Antora cross-component
     xref and a bridge paragraph

3. Apply the standalone coherence pattern:
   ```asciidoc
   TIP: If you have not completed the
   xref:prereq-slug::index.adoc[Prerequisite Workshop], the summary below covers
   what you need to continue.
   ```

**Self-check:**

- [ ] Every module still flows coherently when read standalone
- [ ] Cross-component xrefs use correct Antora syntax (`xref:<slug>::<page>[Title]`)
- [ ] Bridge paragraphs provide enough context for standalone learners
- [ ] Module summaries still accurately describe what the module covers
- [ ] Balanced fences, subs correct, no TODO markers introduced

---

## Phase C — Depth Audit

**Goal:** Find documented-but-uncovered workflows and add them as depth
exercises where they fit the workshop's scope.

**Process:**

1. Compare product documentation coverage against workshop content:
   - List every workflow, procedure, and configuration option in the docs
   - List every exercise in the workshop
   - Identify gaps (documented workflows not covered)

2. For each gap, assess scope:
   - Is it within the RAC requirements? → Add as a depth exercise
   - Is it out of scope? → Note in a gap report, do not add
   - Is it a stretch goal? → Add as a collapsible optional section

3. When adding a depth exercise:
   - Place it where it fits the module progression (usually as an additional
     exercise at the end of the relevant module, before the summary)
   - Follow all WORKSHOP-COMMON-RULES conventions (execute blocks, verify
     sections, prose style)
   - Ground every command in the doc extraction

4. Sync RAC requirements after adding:
   - Update `requirements/<slug>-module-<NN>.md` with new acceptance criteria
   - `decided validate .` and `decided relationships . --validate` must exit 0

**Self-check:**

- [ ] New exercise fits the module's learning progression
- [ ] Commands are grounded in product docs
- [ ] `=== Verify` section has concrete expected output
- [ ] RAC requirements updated and validated
- [ ] Module summary updated to reflect the new exercise

## Integration with workshop-act

These phases slot into the existing pipeline between verify-content (Step 5b)
and the fix-and-test loop (Step 6):

```
Step 5b: verify-content quality gate
    ↓
Step 5c: Post-enrichment audit (this reference)
    Phase A: Correctness (requires doc extractions)
    Phase B: Deduplication (requires catalog context)
    Phase C: Depth (requires doc extractions + RAC)
    ↓
Step 6: Fix-and-test loop (existing)
```

Each phase that produces fixes triggers a rebuild (`make build`) and a re-run of
verify-content before proceeding to the next phase. If no fixes are needed in a
phase, skip the rebuild and move on.

**Reporting:** Each phase produces a structured summary:
- Files changed
- What was fixed/added per file
- Doc evidence used
- Gaps found (for Phase C)
- RAC validation results (for Phase C)
